# STEP 2: SOFTWARE ARCHITECTURE (CONTINUED)

## 8. Search Layer
*   **Technology:** Typesense or Elasticsearch (Vector DB handles AI RAG, but this handles fast exact-match and typo-tolerant keyword search).
*   **Responsibilities:** Fast retrieval of tasks, projects, and documents via inverted indexes. Syncs incrementally from the main PostgreSQL database via CDC (Change Data Capture) using Debezium.

## 9. Notification Layer
*   **Technology:** Novu or custom Node.js service (SendGrid for Email, Firebase FCM for Push, WebSockets for In-App).
*   **Responsibilities:** Routes events (e.g., "@mention in comment") to the appropriate channel based on user preferences. Batches notifications to prevent spam.

## 10. Caching Layer
*   **Technology:** Redis (Cluster Mode).
*   **Responsibilities:** 
    *   Caches frequent queries (e.g., Workspace settings, User Permissions).
    *   Stores short-lived session states.
    *   Provides Distributed Locking for concurrent critical actions.

## 11. Background Jobs & Message Queue
*   **Technology:** BullMQ (backed by Redis) or RabbitMQ.
*   **Responsibilities:** Offloads heavy processing from the main event loop (e.g., generating weekly analytics reports, batch importing CSVs, triggering webhook payloads to third-party integrations).

## 12. File Storage
*   **Technology:** AWS S3 or Cloudflare R2.
*   **Responsibilities:** Stores immutable binary assets (images, PDFs). Access is secured via Signed URLs generated by the API.

## 13. Logging, Monitoring & Analytics
*   **Logging:** Winston/Pino -> Logstash -> Elasticsearch -> Kibana (ELK stack) or Datadog. Correlates logs using a unique `trace_id` per request.
*   **Monitoring:** Prometheus & Grafana. Monitors CPU/Memory, Node.js event loop lag, and API error rates.
*   **Analytics:** PostHog for tracking user behavior (feature usage, funnel conversion) and Sentry for frontend/backend error tracking.

## Communication Between Layers
1. **Client to Presentation/API Layer:** The Next.js frontend sends standard HTTP GET/POST/PUT/DELETE requests to the REST API for static data mutations. For real-time updates (like the 3D workspace state or document editing), it establishes a persistent WebSocket connection.
2. **API to Business/Service Layer:** Controllers receive HTTP requests, parse DTOs (Data Transfer Objects), and invoke specific Service functions (e.g., `TaskService.createTask()`).
3. **Service Layer to Repository/Data Layer:** The Service layer does not write SQL. It calls the Repository layer (Prisma), which translates object actions into optimized SQL queries or Redis commands.
4. **Service Layer to Background Jobs:** If a task requires heavy processing, the Service layer pushes a job payload to BullMQ and immediately returns a `202 Accepted` to the client. The Worker picks up the job, processes it, and updates the database, optionally triggering a WebSocket event to notify the client when done.
5. **Cross-Service Communication:** Handled via Redis Pub/Sub (for real-time events) or gRPC (for high-speed microservice-to-microservice calls, like calling the Python AI Service from Node.js).
